# Auditoría Eros — 2026-07-04

Auditoría inmersiva de todo el sistema: filosofía/docs, motor de scripts, memoria/design-intelligence, agentes/workflow, CLI + panel, e higiene de repo. Objetivo: que Eros funcione de punta a punta como director creativo autónomo, sin fricciones ni contradicciones entre lo que los docs prometen y lo que el código realmente hace.

**Contexto clave antes de leer esto:** el último commit (`30b840f`) es del 2026-05-24. Hay ~6 semanas de trabajo sin commitear sentado en el working tree — un refactor completo y coherente de `scripts/eros-core/` hecho en una sola sesión (24 may 15:34 → 25 may 01:09). Esta auditoría cae justo en medio de esa reparación a medio terminar. La mayoría de los blockers de abajo son precisamente lo que ese refactor está arreglando (o dejó a medio arreglar).

---

## 1. Resumen ejecutivo

Eros **no es aspiracional** — tiene una memoria real que se auto-critica y evoluciona (`personality.json`), un loop de orquestación real (`state.mjs next/done`), agentes bien definidos y un CLI en Go que efectivamente funciona. El problema no es que el sistema sea humo; es que **hay una fractura de fechas**: un refactor de scripts (rename `.brain` → `.eros`, `archive/` → `eros-core/`) se hizo a medias, y quedaron rutas rotas que impedirían que el loop autónomo corra hoy sin fallar.

Hay **3 blockers concretos** que romperían un "nuevo proyecto" ahora mismo, y son todos del mismo tipo: rutas de scripts que apuntan a archivos que ya no están donde el código cree que están.

## 2. Blockers — rompen el loop autónomo hoy

### 2.1. `eros-orchestrator.mjs` → `init-project.mjs` con ruta rota
`scripts/eros-core/eros-orchestrator.mjs` (~línea 85), en la tarea `setup/create-dir`, ejecuta:
```
cd "$SCRIPTS" && node init-project.mjs ...
```
donde `$SCRIPTS` resuelve a `scripts/eros-core/`. Pero `init-project.mjs` vive en `scripts/pipeline/init-project.mjs`. Es el **primer** `run-script` que se ejecuta después de la entrevista de discovery — es decir, el loop de "nuevo proyecto" fallaría con `MODULE_NOT_FOUND` en el segundo paso.

### 2.2. `eros-orchestrator.mjs` → `eros-server.mjs` no existe
Las tareas `server/start`, `server/stop`, `server/status` (líneas ~286-320) llaman a `node "$SCRIPTS/eros-server.mjs"`. Ese archivo **no existe en ningún lado del repo**. El script real es `scripts/panel/server.mjs`. Estas tareas son necesarias antes de la fase de observación (Phase 3, captura de screenshots contra el dev server vivo) — así que esa fase tampoco puede arrancar el servidor por el camino documentado.

### 2.3. `train-reference.mjs` → `capture-refs.mjs` con ruta relativa rota
`scripts/memory/train-reference.mjs:447-448` (`cmdSession`) hace `path.join(__dirname, 'capture-refs.mjs')`, que resuelve relativo a `scripts/memory/`. Pero `capture-refs.mjs` vive en `scripts/eros-core/`. `npm run eros:ref -- session ...` tira `ENOENT`. (Nota: hay una variable `captureScript` idéntica en la línea 100 pero no se usa ahí — solo la 447-448 ejecuta.)

**Fix sugerido (mismo patrón para las 3):** corregir las rutas para que apunten a la ubicación real post-refactor (`../pipeline/init-project.mjs`, `../panel/server.mjs`, `../eros-core/capture-refs.mjs` según corresponda). Es un fix mecánico, no de diseño — 3 líneas.

## 3. Docs canónicos: uno de los dos "runtime loop" está obsoleto

`AGENTS.md` (línea 148) cita `.eros/pipeline.md` como *la* referencia del runtime loop. Pero lo que `Skill("project")` realmente carga es `.eros/workflows/project.md` (header: "CEO Orchestrator **V8**") — un protocolo completamente distinto, basado en `state.mjs next/done`. `.eros/pipeline.md` está encabezado "Pipeline **V7**" y describe una secuencia manual vieja, invocando scripts con rutas planas (`node eros-context.mjs`, `node eros-gate.mjs`, `node eros-log.mjs`, `node eros-doctor.mjs`, `node eros-train.mjs`) que **no existen como archivos sueltos en `scripts/`** — viven en `scripts/eros-core/`, `scripts/memory/`, `scripts/dev/`.

`project.md` ya fue reparado (en el working tree, sin commitear) con las rutas correctas. `pipeline.md` nunca recibió el mismo arreglo. Como `AGENTS.md` sigue apuntando a `pipeline.md` como canónico, un agente que siga la documentación al pie de la letra termina en el archivo equivocado.

**Fix sugerido:** o bien archivar `pipeline.md` como superado por V8 y repuntar `AGENTS.md` a `.eros/workflows/project.md`, o aplicarle el mismo parche de rutas que ya se le hizo a `project.md`. La primera opción es más limpia — mantener dos "fuentes de verdad" del mismo loop es justamente lo que causó esta clase de bug.

Nota menor: el resumen de 7 pasos del "Autonomous Brain Loop" dentro de **AGENTS.md mismo** (líneas 49-57) describe el loop manual estilo V7, no el contrato V8 next/done — es la misma deriva documental, pero adentro del propio archivo.

`node .eros/scripts/eros-doctor.mjs` da `All checks passed.` — el health-check valida existencia de estructura de carpetas, no consistencia de comandos entre documentos, así que este tipo de desfase es invisible al gate que `AGENTS.md` exige pasar antes de abrir/actualizar un PR.

Todo lo demás en la capa de docs está sano: el roster de agentes (`designer`, `builder`, `polisher`, `evaluator`, `reference-analyst`) es idéntico entre `CLAUDE.md`, `AGENTS.md` y los archivos reales en `.claude/agents/` y `.eros/agents/`; los hooks de `.claude/settings.json` (`SessionStart` leyendo `EROS.md`+`AGENTS.md`, hooks de compact/resume leyendo `personality.json`) apuntan a archivos que existen y funcionan de verdad — la promesa de EROS.md ("leer personality.json al inicio de cada conversación") se cumple mecánicamente, no solo en prosa.

## 4. Motor de scripts (`scripts/eros-core/` y alrededores)

**El diagnóstico central: esto no es duplicación, es una reparación en curso de un bug real.** El 2026-04-14 (commit `7944c4f`) se archivó `eros-orchestrator.mjs` y `capture-refs.mjs` como "huérfanos" tras una auditoría — pero `scripts/eros-core/state.mjs` (líneas 720 y 752) hace `import('./eros-orchestrator.mjs')` **dinámico** dentro de `next`/`done`, y un grep de imports estáticos no lo detectó. Resultado: desde `7944c4f` hasta el HEAD actual, **`state.mjs next` y `state.mjs done` estuvieron rotos** — el loop entero de `.eros/workflows/project.md` depende de ese import. El working tree de ahora mismo restaura el archivo de vuelta a `scripts/eros-core/` — confirmado, `node --input-type=module -e "import('./scripts/eros-core/eros-orchestrator.mjs')"` ya funciona con los cambios sin commitear.

Los 5 archivos nuevos con prefijo `eros-` (`eros-context.mjs`, `eros-gate.mjs`, `eros-state.mjs`, `eros-memory.mjs`, `eros-observer.mjs`) **no son duplicados** de `context.mjs`/`gate.mjs`/`state.mjs` — son shims de compatibilidad de ~10-13 líneas que hacen `spawn` hacia el archivo real, con comentarios explícitos explicando que el prefijo `eros-` se sacó en el rename `brain→eros-core` pero algunos callers todavía invocan el nombre viejo.

**Docs desactualizados que quedan contradiciendo la reparación una vez que se commitee:**

**14 scripts nuevos de captura (`analyze-ref.mjs`, `grab-deep/hero/nav/shader/structure.mjs`, `shot-bottom/cursor/full/hover/page/preloader/section/view.mjs`, `scroll-capture.mjs`):** ninguno importa `scripts/lib/utils.mjs` — cada uno reimplementa a mano el mismo boilerplate de Puppeteer (`puppeteer.launch({headless:'new', args:[...]})` + viewport). No quedó claro, revisando `project.md` y `gate.mjs`, si el veredicto del evaluator LLM alimenta al gate determinístico o si corren en paralelo sin comunicarse. Si el evaluator dice RETRY y el gate dice APPROVE (o viceversa), ¿cuál manda?
